### PART 1: PROJECT FOUNDATION

#### 1.1 Why This Project Exists
The industry is stuck at Level 1 of AI Agents. We have thousands of demos, chatbots, and LangChain wrappers that call an LLM. We do not have the equivalent of Kubernetes for AI Agents.

Every team building production autonomous agents today is forced to re-invent:
1.  Execution engine with retries, timeouts, and sandboxing
2.  Stateful memory and context management
3.  Workflow DAG orchestration
4.  Tool registry and capability discovery
5.  Secure credential vault for tools
6.  Observability for non-deterministic systems
7.  Cost, latency, and reliability controls across providers

**Aether exists to solve the infrastructure problem, not the prompting problem.** We are building the control plane. Others will build the agents.

#### 1.2 Mission
Provide a cloud-native, provider-agnostic, secure and observable control plane that allows any engineering team to run 10,000 autonomous agents in production as easily as they run containers today.

#### 1.3 Vision [12 Months]
A self-hostable platform where a developer can: `register an agent spec -> attach tools & memory policies -> deploy a workflow -> observe execution traces -> scale to zero to thousands`.

#### 1.4 Long-Term Vision [3 Years]
Aether becomes the open standard for Agent Infrastructure.
1.  **The Linux of Agents:** An open-source core with enterprise extensions.
2.  **The Stripe for Agent Capabilities:** A marketplace for tools, memory providers, and evaluation harnesses.
3.  **Multi-tenant Cloud:** Aether Cloud offering where Aether manages the control plane globally.

#### 1.5 Problem Statement
Building autonomous agents in production is an infrastructure problem characterized by:
*   **Non-deterministic execution:** Traditional request/response monitoring breaks.
*   **Long-running, stateful workflows:** Jobs run for minutes to hours, not milliseconds.
*   **Provider coupling:** Teams are locked into OpenAI/Anthropic due to lack of abstraction.
*   **Security blast radius:** Agents have access to tools, browsers, and code execution.
*   **No standard primitives:** No equivalent of Pod, Service, Deployment for agents.

#### 1.6 Goals [For V1.0]
1.  **G1 - Agent Lifecycle Management:** Create, version, rollback, deprecate agents declaratively.
2.  **G2 - Reliable Execution:** At-least-once execution with idempotency keys, timeouts, retries, and dead-letter queues.
3.  **G3 - Stateful Orchestration:** DAG-based workflow engine for multi-agent collaboration.
4.  **G4 - Provider Agnostic:** Works with any LLM provider, vector store, and queue.
5.  **G5 - Production Hardened:** AuthN/Z, audit logs, secret isolation, rate limiting, cost guards.
6.  **G6 - Full Observability:** Every agent run produces OpenTelemetry traces, logs, metrics, and execution replay.

#### 1.7 Non-Goals [What We Will NOT Do in V1.0]
1.  We will NOT build a chat UI. That is a reference app, not the product. API-first.
2.  We will NOT build our own LLM. We consume models.
3.  We will NOT build a prompt engineering IDE. Tools like LangSmith already do this.
4.  We will NOT build a vector database. We integrate with existing ones.
5.  We will NOT support no-code builders in V1.0. Our user is a developer.

#### 1.8 Target Users
Primary: **Platform Engineer / Backend Engineer** at a startup building an AI product. They have hit scaling pains with their homegrown agent runner.
Secondary: **AI Engineer** who needs to productionize a research agent.
Tertiary: **Enterprise Architect** who needs governance over autonomous agents.

#### 1.9 Product Philosophy
1.  **API First, UI Second:** Every feature is an API. The dashboard is a consumer of the API.
2.  **Declarative, not Imperative:** Users declare *what* agent should do, not *how* infra runs it. Like Kubernetes manifests.
3.  **Boring Infrastructure, Exciting Agents:** Use Postgres, Redis, gRPC, Kafka patterns. Don't invent new databases.
4.  **Explainability is a Feature:** Every decision the control plane makes is auditable.
5.  **Fail Open to Logs, Closed to Security:** An agent failure should be observable, not a security breach.

#### 1.10 Engineering Philosophy
1.  We optimize for maintainability over velocity in Month 0-3.
2.  We optimize for velocity over novelty in Month 4-10.
3.  We optimize for stability over everything in Month 10-12.
We do not move fast and break things. We move deliberately and build things that don't break.

#### 1.11 Success Metrics [V1.0 Launch Criteria]
*   **Engineering:** 80%+ test coverage on core services, p95 API latency <150ms, <0.1% job loss under failure injection, 100% of config via env, zero secrets in git.
*   **Product:** Can execute a 5-agent collaborative research workflow that runs for 15 mins, uses 3 tools, survives worker pod restart, and is fully traceable.
*   **Adoption:** A new backend engineer can deploy Aether locally with `docker-compose up` in <5 mins and execute first agent in <15 mins.

#### 1.12 Project Constraints
*   Solo / small team -> Modularity is survival.
*   Budget -> Must run on a single cheap VM initially, scale horizontally later.
*   No dedicated SRE initially -> Must be simple to operate.

#### 1.13 Scope [V1.0 Boundary]
IN: Registry, Execution Engine, Memory Engine abstraction, Workflow Engine v1, Scheduler, Provider Layer, Observability stack, Auth v1.
OUT: Multi-region, Multi-tenancy with hard isolation, Visual workflow builder, Marketplace, Billing.

#### 1.14 Future Vision
V1.0 is a performant, secure, observable Modular Monolith.
V1.5 is a distributed system with separated control/data plane.
V2.0 is a multi-tenant cloud.

### PART 2: ENGINEERING PRINCIPLES

#### 2.1 Design Before Code
No ticket moves to implementation without an RFC or ADR for non-trivial changes. Example: Before adding Redis Streams, write an RFC comparing Redis Streams vs Kafka vs Postgres SKIP LOCKED for job queue in Aether context. Output is a design doc, not code.

#### 2.2 Documentation First
Documentation is not a chore after code. It is the design. The README for a service is written *before* the service. Example: `docs/architecture/execution-engine.md` must describe state machine, failure modes, and APIs before any worker code is merged.

#### 2.3 Architecture Driven Development
Every story maps to a component in `docs/blueprint/C4-model.md`. If it doesn't fit the architecture, the architecture is wrong and must be updated via ADR first. We never code "off blueprint".

#### 2.4 Infrastructure First
`infra/` exists from Day 1. Dockerized local setup, migrations, CI pipeline are built before Agent business logic. Principle: If you can't run it cleanly on your machine, you can't ship it.

#### 2.5 Test Driven Thinking
Not strict TDD, but we think about testing first. For each feature we ask: "How will we test failure injection?" Example: The Execution Engine must have a test that kills worker mid-step and asserts job requeues.

#### 2.6 Provider Agnostic Architecture
Every external dependency is behind an interface/port. Example: `LLMProvider` interface with `OpenAIAdapter`, `AnthropicAdapter`, `LocalVLLMAdapter`. No `import openai` allowed outside `libs/providers/llm/`. This is enforced by lint rule.

#### 2.7 Scalable by Default
We assume 10x traffic tomorrow. Design choices: stateless API servers, stateful workers with idempotency, Postgres with connection pooling, pagination everywhere, no N+1 queries.

#### 2.8 Security by Default
1. Zero Trust between services even inside monolith -> internal auth tokens.
2. Secrets only via Vault/ENV manager, never hardcoded.
3. Agent tool calls run in sandboxed workers with gVisor/Firecracker mindset.
4. RBAC for all APIs from Day 1, even if single user.

#### 2.9 Observability by Default
Every request gets `X-Request-ID` and `X-Trace-ID`. Every agent run produces an OpenTelemetry trace. We log in JSON structured format. Metrics are Prometheus-style. If you can't see it in Grafana, it didn't happen.

#### 2.10 Simple Before Clever
Prefer boring, well-understood tech. Use Postgres queue before Kafka. Use modular monolith before microservices. Prefer 100 lines of clear code over 10 lines of clever code. We don't introduce a service mesh in V1.0.

#### 2.11 No Premature Optimization
Don't cache until metrics prove slowness. Don't shard until Postgres hurts. But instrument everything so you KNOW when to optimize. Performance checklist must show p95 degradation before caching layer is approved.

#### 2.12 Modular Monolith First
We build ONE deployable with strictly bounded modules: `com.aether.registry`, `com.aether.execution`, `com.aether.memory`. Module can only talk via public interface, not internal tables. This lets us extract to microservice later without rewrite. This is how Shopify, Uber, and Team at Google start V1 systems.

#### 2.13 AI Assists Implementation But Never Architecture
AI tools are forbidden from creating RFCs, ADRs, or high-level architecture. They are excellent at generating boilerplate, tests, repetitive CRUD from a well-defined spec. Human decides WHAT and WHY, AI helps with HOW (implementation).

### PART 3: PROJECT ORGANIZATION

#### 3.1 Repository Structure [Monorepo - Modular Monolith]
We use a monorepo. Polyrepo is premature for V1.

```
/
├── docs/                      # THE SOURCE OF TRUTH
│   ├── blueprint/             # C4 Model, System Context
│   ├── rfc/                   # Request For Comments [numbered]
│   ├── adr/                   # Architecture Decision Records [numbered]
│   ├── api/                   # OpenAPI specs
│   ├── runbooks/              # Operational runbooks
│   └── learning/              # Learning notes per phase
├── apps/
│   ├── control-plane-api/     # Main Go/Node API [Module host]
│   └── dashboard/             # Next.js reference UI [consumer only]
├── services/                  # Bounded contexts as modules inside monolith
│   ├── registry-service/
│   ├── execution-engine/
│   ├── memory-engine/
│   ├── workflow-engine/
│   └── provider-gateway/
├── libs/                      # Shared libraries
│   ├── common/                # logger, config, errors
│   ├── providers/             # LLM, VectorDB, Queue adapters
│   └── sdk/                   # Aether Client SDK
├── infra/
│   ├── docker/
│   ├── k8s/                   # manifests + helm
│   ├── terraform/             # AWS/GCP foundation
│   └── migrations/
├── .github/workflows/         # CI/CD
├── .cursor/rules/             # AI cod rules
├── Makefile
└── README.md
```

#### 3.2 Documentation Structure
Docs are versioned and numbered: `RFC-0001-queue-technology.md`, `ADR-0005-modular-monolith.md`. Never `rfc-final-final.md`.

#### 3.3 Branch Strategy - Trunk Based Development
As used at Google and OpenAI for platform teams.
*   `main` is always deployable.
*   `feat/<issue-id>-short-desc` - lifespan <2 days. Merge via PR.
*   No long-lived `dev`, `develop` branches.
*   Feature flags for incomplete work, not feature branches.

#### 3.4 Git Workflow
1.  Issue -> Branch -> Commit -> PR -> Review -> CI Green -> Squash Merge -> Delete Branch.
2.  **Conventional Commits:** `feat(registry): add agent versioning` , `fix(exec): handle timeout leak` , `docs(rfc): add provider layer`.
3.  PR Template enforces: Linked Issue, RFC/ADR link, Testing evidence, Screenshots for API/Trace.

#### 3.5 Naming Conventions
*   Branches: `feat/AET-123-execution-retry`
*   Services: `aether-registry`, `aether-exec-engine`
*   Envs: `AETHER_DB_URL` , `AETHER_LLM_PROVIDER`
*   API paths: `/api/v1/agents`, `/api/v1/runs/{runId}`
*   DB tables: `snake_case` - `agent_runs`, `agent_specs`

#### 3.6 Versioning Strategy
*   **Git Tags:** Semantic Versioning `v0.1.0-alpha`, `v1.0.0`. V1.0 is not `v1`.
*   **API Versioning:** URI versioning for now `/api/v1/`. No breaking changes inside v1 without ADR.
*   **Agent Spec Version:** Every agent has `spec_version` integer for backward compat.

#### 3.7 Release Strategy
*   Inner loop: Local -> `main`
*   Outer loop: `main` -> Staging [on K8s cluster auto deploy] -> Production [manual approval + tag]
*   Release Notes auto-generated from conventional commits + manual highlight.
*   Every release has migration plan + rollback plan in runbook.

#### 3.8 Issue Management, Labels, Milestones, Boards
Tool: GitHub Projects or Linear. Single board.

*   **Labels:** `type:feature`, `type:bug`, `type:rfc`, `type:docs`, `area:execution`, `area:registry`, `priority:P0-P3`, `risk:high`, `needs:rfc`
*   **Milestones = Phases:** Phase-1-Platform-Foundation, Phase-2-Registry...
*   **Project Boards Columns:** Backlog -> Ready -> In Design [RFC] -> In Dev -> In Review -> In QA -> Done. No issue can be In Dev if it has `needs:rfc` label.

### PART 4: ENGINEERING DOCUMENTS

Every document has YAML Frontmatter: Author, Date, Status [Draft, Review, Approved, Deprecated], Linked Issues.

**1. Engineering Blueprint:** `docs/blueprint/README.md`. Contains C4 diagrams: Context [External systems], Container [API, Workers, DB, Redis], Component [Modules inside API], Code. Owner: Principal Engineer. Written in Week 1, updated every Phase. Evolves via ADR.

**2. RFC [Request for Comments]:** For significant decisions that are reversible but need alignment. e.g., "Which queue should we use?". Template includes: Summary, Context, Goals/Non-Goals, Proposal with Alternatives considered [crucial], Tradeoffs, Migration plan, Risks, Open Questions. Who writes: Feature Owner. When: BEFORE implementation of any Epic. How evolves: Comments in PR, status goes to Accepted/Rejected.

**3. ADR [Architecture Decision Record]:** For irreversible or hard-to-reverse decisions that were MADE. Immutable once Approved. Example: ADR-0001: "We will start with Modular Monolith over Microservices". Format: Title, Status, Context, Decision, Consequences [positive and negative], Alternatives. Who writes: Who made decision. When: Immediately AFTER an RFC is accepted or when an on-the-fly decision was made. Stored forever.

**4. Roadmap:** `docs/ROADMAP.md` - auto-linked to milestones. Human readable narrative.

**5. Runbooks:** `docs/runbooks/` - e.g., `runbook-incident-execution-stuck.md`. Contains Symptoms, Diagnosis queries, Recovery steps, Escalation. Written when a service goes to staging for first time.

**6. Architecture Documents:** Per service deep dive: `docs/architecture/execution-engine.md` - State machine diagram, Data model, API sequence, Failure modes.

**7. API Docs:** Generated from OpenAPI spec `docs/api/openapi.yaml`. Source of truth is spec, not code. Code implements spec.

**8. Database Docs:** `docs/database/schema.md`, `docs/database/migrations-strategy.md` - Every table purpose, indexing strategy, ownership.

**9. Deployment Docs:** `docs/deployment/local.md`, `staging.md`, `production.md` - Step-by-step. Must be executable by new hire.

**10. Security Docs:** `docs/security/threat-model.md` - Data flow, trust boundaries, secrets management, RBAC model.

**11. Monitoring Docs:** `docs/observability/metrics-catalog.md` - Every metric, trace attribute, log field defined.

**12. Release Notes:** `docs/releases/v0.x.md`.

**13. Contributing Guide:** `CONTRIBUTING.md` - How to setup, how to contribute, DoD.

**14. Definition of Done:** `docs/DoD.md` - Reusable checklist.

### PART 5: COMPLETE DEVELOPMENT METHODOLOGY

This is the mandatory lifecycle. No shortcuts.

**Stage 1: Problem Statement [1-2 paragraphs]**
Why are we doing this? What user pain does it solve? Example: "Agents fail silently and cannot be retried, leading to customer SLA breach."
Output: GitHub Issue with clear pain.
Common Mistake: Writing solution as problem. "We need Redis" is not a problem.

**Stage 2: Requirements [Functional + Non-Functional]**
Functional: API endpoints, user flows. Non-Functional: p95 <200ms, must support 100 concurrent runs, must be audit logged.
Output: Updated Issue or PRD md.
Common Mistake: Missing NFRs. Backwards compatibility is forgotten.

**Stage 3: Research [2-4 hours timebox]**
Look at how Temporal, Airflow, Kubernetes Jobs solve similar problem. Document in RFC under "Alternatives Considered".
Output: Links, notes in RFC draft.
Common Mistake: Researching forever. Timebox it.

**Stage 4: RFC [If Epic or Features with risk]**
Write RFC. Must be reviewed by at least 1 peer [or rubber-duck with AI for architecture critique, but human decides]. Not required for small bugfix Story, required for Epic.
Output: `docs/rfc/RFC-xxxx.md` with Status: Approved.
Common Mistake: RFC that is too long, no tradeoffs.

**Stage 5: Architecture [C4 Component Level]**
Update blueprint diagrams. Define module boundaries, interfaces, data flows. For Aether, this means defining ports/adapters.
Output: Diagram + interface definition.
Common Mistake: Leaky abstraction.

**Stage 6: ADR [After Architecture Decision]**
If decision is irreversible, write ADR immediately.
Output: ADR markdown file.
Common Mistake: Writing ADR before decision finalized.

**Stage 7: Task Breakdown [Epic -> Stories -> Tasks]**
Decompose to <1 day tasks. Must include docs tasks, tests tasks, infra tasks, not just code.
Output: Sub-issues linked.
Common Mistake: 5-day tasks that are unreviewable.

**Stage 8: Sprint Planning**
Pick tasks for sprint based on Phase goal. Capacity: 70% dev, 20% docs/tests/reviews, 10% buffer.
Output: Sprint board.

**Stage 9: AI Prompt [Critical Step]**
Before using AI, write a detailed implementation prompt. It must contain: Context [link to RFC/ADR], File structure to touch, Acceptance criteria [from DoD], Non-goals, Test scenarios. This is "Context Engineering" for AI.
Example for Cursor: "@registry-service Read docs/adr/ADR-0002... Implement idempotent agent creation API following blueprint..."
Output: Saved prompt in issue comment.

**Stage 10: Implementation**
Human + AI pair. AI generates 70%, Human refactors and secures 30%. Follow modular monolith boundaries. No direct provider imports.
Output: PR.

**Stage 11: Code Review**
Checklist enforced: Architecture alignment?, Security?, Observability?, Tests?, Docs? Reviewer must run locally.
Common Mistake: LGTM reviews without pulling branch.

**Stage 12: Refactoring**
After PR approval, before merge, ask: "Is this the simplest design?" Remove dead code, improve naming. No functionality change.

**Stage 13: Testing**
Unit + Integration + Failure injection. For Execution Engine: Test for worker crash. For API: Contract test. Must show evidence in PR.
Common Mistake: Only happy path tests.

**Stage 14: Documentation**
Update API docs, runbook, README, architecture doc if behavior changed. PR fails if docs not updated for observable behavior.

**Stage 15: Release**
Merge to main -> Auto deploy to staging -> Manual smoke test from runbook -> Tag release -> Deploy to prod -> Update Release Notes -> Announce in changelog.

### PART 6: ROADMAP - Layers > Phases > Milestones > Epics > Stories

We organize as Layers representing architectural maturity.

**LAYER 0: ENGINEERING FOUNDATION & DEVELOPER EXPERIENCE [Weeks 0-4]**
*Philosophy: Build the factory before the product.*

**Phase 0: Empty Repo to Engineering Foundation**
*   Goal: Any engineer can clone and `make dev` in 5 mins.
*   Deliverables: Repo scaffolding, monorepo tooling, Makefile, docker-compose for Postgres/Redis/OTEL, CI pipeline [lint/test/build], docs structure, blueprint v0, CONTRIBUTING.md, DoD.
*   Knowledge Gained: Monorepo management, trunk development, documentation-as-code.
*   Exit Criteria: CI green, PR template works, `docs/blueprint` has C4 Context diagram.
*   Duration: 2 weeks.
*   Dependencies: None.
*   Risks: Overengineering infra too early. Mitigation: Use `docker-compose`, not K8s yet.
*   Epics: E0.1 Repo & CI, E0.2 Local Dev Env, E0.3 Documentation Scaffolding.

**LAYER 1: PLATFORM FOUNDATION [Weeks 4-10]**

**Phase 1: Platform Core & API Skeleton**
*   Goal: Modular Monolith skeleton running with health checks, config, structured logging, OTEL.
*   Deliverables: `control-plane-api` with module loader, `/health`, `/ready`, config via env, logger, error handler, API versioning middleware, Prometheus metrics.
*   Knowledge: Clean Architecture / Hexagonal, graceful shutdown, config management.
*   Exit Criteria: `GET /api/v1/health` returns 200 with traces in Jaeger locally.
*   Duration: 2 weeks.
*   Risks: Choosing wrong web framework. Mitigation: ADR for framework choice.
*   Epics: E1.1 API Framework & Middleware, E1.2 Observability Plumbing, E1.3 Config & Error handling.

**Phase 2: AuthN & AuthZ & Tenancy**
*   Goal: Secure the platform from day 1.
*   Deliverables: JWT auth with API keys, RBAC [admin, developer, runner], Organization model, API key issuance/rotation, audit log table.
*   Knowledge: JWT, RBAC, multi-tenancy patterns [row-level].
*   Exit Criteria: All API calls require auth except `/health`; tests for unauthorized access.
*   Duration: 2 weeks.
*   Epics: E2.1 API Key Auth, E2.2 RBAC, E2.3 Org Tenancy.

**LAYER 2: AGENT CONTROL PLANE CORE [Weeks 10-22]**

**Phase 3: Agent Registry Engine**
*   Goal: CRUD+Versioning for Agent Specs. The source of truth.
*   Deliverables: `registry-service` module, AgentSpec model [name, description, llm_config, tool_whitelist, memory_policy], Postgres tables, versioning logic, OpenAPI spec, SDK methods.
*   Knowledge: Schema design, versioning patterns, immutability.
*   Exit: Can register agent v1, v2, rollback, list versions with SDK. DB docs written.
*   Duration: 3 weeks.

**Phase 4: Execution Engine [Heart of Aether]**
*   Goal: Reliably execute a single agent run.
*   Deliverables: `execution-engine`, Job queue abstraction [Redis Stream interface], Worker pool, State machine [Queued->Running->Paused->Completed/Failed], timeout/retry/dead-letter, Idempotency, Execution trace storage.
*   Knowledge: Distributed jobs, state machines, idempotency, poison messages.
*   Exit: A worker crashing mid-run requeues job; p95 enqueue <50ms. Failure injection tests pass.
*   Duration: 4 weeks. Highest risk phase.
*   Risks: Queue durability. Mitigation: RFC-0002 queue tech.

**Phase 5: Memory Engine**
*   Goal: Stateful context for agents.
*   Deliverables: Memory abstraction [Short-term: Redis, Long-term: Postgres+VectorDB], Memory policy per agent, Session management, Context window compression strategy interface.
*   Knowledge: RAG, embeddings, chat history management, token budgeting.
*   Exit: Agent run can read/write episodic memory, and retrieval works via provider interface.
*   Duration: 3 weeks.

**LAYER 3: ORCHESTRATION & INTELLIGENCE [Weeks 22-34]**

**Phase 6: Provider Layer & Gateway**
*   Goal: Provider agnosticism.
*   Deliverables: `provider-gateway` module, Interfaces: LLMProvider, ToolProvider, VectorProvider. Adapters: OpenAI, Anthropic, Postgres PGVector. Cost metering hook.
*   Knowledge: Adapter pattern, rate limiting, circuit breaker.
*   Exit: Switch OpenAI->Anthropic via config change only. No code change.
*   Duration: 2 weeks.

**Phase 7: Workflow Engine [DAG]**
*   Goal: Multi-agent orchestration.
*   Deliverables: Workflow Spec [DAG JSON], Workflow exec, Fan-out/fan-in, Human-in-the-loop pause, Sub-workflow call. Uses Execution Engine underneath.
*   Knowledge: DAG orchestration [like Airflow/Temporal], workflow patterns.
*   Exit: Can execute 3 agents sequentially where output of A is input to B.
*   Duration: 3 weeks.

**Phase 8: Scheduler & Event Bus**
*   Goal: Time and Event driven agents.
*   Deliverables: Cron scheduler for agents, Webhook ingress, Event bus [internal pub/sub], Integration triggers.
*   Knowledge: Cron, idempotent scheduling, webhook security.
*   Exit: Schedule agent every 5 min reliably.
*   Duration: 2 weeks.

**Phase 9: Tool Registry & Sandboxing**
*   Goal: Secure tool execution.
*   Deliverables: Tool Spec [OpenAPI for tools], Credential vault reference, Sandboxing wrapper executor, Rate limiting per tool.
*   Knowledge: Tool security, secret isolation, sandboxing.
*   Exit: Agent can call HTTP tool with injected secret without seeing secret value in logs.
*   Duration: 2 weeks.

**LAYER 4: PLATFORM HARDENING [Weeks 34-44]**

**Phase 10: Observability & Analytics**
*   Goal: Make white-box.
*   Deliverables: Execution timeline viewer API, Cost & latency analytics per agent/run/tool, Alerting rules for failed runs, Grafana dashboards JSON in infra/, Log aggregation queries.
*   Knowledge: OTEL deep dive, Prometheus metrics design.
*   Exit: Dashboard shows cost per run, trace replay works.
*   Duration: 3 weeks.

**Phase 11: Security Hardening & Performance Guards**
*   Goal: Production readiness.
*   Deliverables: Threat model implementation check, Rate limiting per org, Quota management, Circuit breakers, Load tests with k6, Security runbook.
*   Knowledge: System hardening, load testing.
*   Exit: Passes security checklist, handles 100 concurrent runs on single node without job loss.
*   Duration: 3 weeks.

**LAYER 5: DISTRIBUTION & SCALE [Weeks 44-52]**

**Phase 12: Cloud Deployment & Open Source Launch**
*   Goal: Ship V1.0.
*   Deliverables: Helm chart, Terraform for AWS/GCP, K8s deployment docs, `docker-compose.prod.yml`, OSS LICENSE, public README with architecture diagram, CONTRIBUTING, Issue templates, Blog post draft, Example agents repo.
*   Knowledge: K8s, Helm, Terraform, OSS community building.
*   Exit: External user can deploy Aether on their K8s in <30 mins via Helm + run example. Tag v1.0.0.
*   Duration: 4 weeks.

### PART 7: COMPLETE LEARNING ROADMAP

**Why per Phase:** Learn just-in-time, not just-in-case. Each concept is tied to a concrete deliverable.

**Phase 0 [Foundation]:** Backend: Monorepos, Makefile. Arch: C4 model, Modular Monolith vs Microservices. Cloud: Docker & Docker Compose deep dive, 12-factor app. DevOps: GitHub Actions CI/CD. WHY: You need to understand factory before product.

**Phase 1 [API Skeleton]:** Backend: Clean/Hexagonal Architecture, Middleware pattern, Graceful shutdown, Config management [Viper/env]. Networking: HTTP lifecycle, gRPC vs REST, health check patterns. Observability: Structured logging [zerolog/pino], OpenTelemetry basics [trace, span]. WHY: Core platform patterns.

**Phase 2 [Auth]:** Backend: JWT, PASETO, API key hashing [bcrypt/argon2], RBAC vs ABAC. Security: OWASP Top 10, Secret management, Audit logging. DB: Row Level Security in Postgres, Tenancy models [shared table]. WHY: Security must be designed early.

**Phase 3 [Registry]:** DB: Postgres advanced [indexes, JSONB, migrations, constraints], Schema versioning & immutability. API: OpenAPI spec first, pagination, versioning. WHY: Registry is source of truth, DB design critical.

**Phase 4 [Execution Engine]:** Backend: Queues [Redis Streams, Kafka concepts], Workers, State Machines, Idempotency keys, Retries w/ exponential backoff + jitter, Dead-letter queue, Poison pill handling. Distributed Systems: At-least-once vs Exactly-once, Distributed locks, Failure detection. WHY: Hardest distributed system problem.

**Phase 5 [Memory]:** AI Infra: Embeddings generation, Vector DB concepts [HNSW, cosine], RAG pattern, Context window management [sliding window, summarization], LLM: Token counting, Context Engineering. DB: Redis data structures, Postgres pgvector extension. WHY: Memory is differentiator for AI Agents.

**Phase 6 [Provider Layer]:** Arch: Adapter & Strategy patterns, Port/Adapter, Circuit Breaker [resilience4j], Rate Limiter token bucket. Networking: HTTP retries, timeout handling. WHY: Provider agnosticism requires excellent abstraction design.

**Phase 7 [Workflow]:** Arch: DAGs, Workflow engines [Temporal, Airflow concepts], Saga pattern [for failure], Fan-out/fan-in, Idempotency in workflows. DB: Recursive queries for DAGs if needed. WHY: Multi-agent orchestration is core value prop.

**Phase 8 [Scheduler]:** Backend: Cron parsing, Leader election for scheduler [if distributed], Webhook signing verification, Event-driven architecture. Queues: Pub/Sub patterns. WHY: Time/event driven agents unlock real use cases.

**Phase 9 [Tools]:** Security: Sandboxing concepts [gVisor, Docker seccomp], Principle of Least Privilege, Secret injection, Tool auth types [OAuth, API Keys]. Arch: Tool registry design. WHY: Tools are biggest attack vector.

**Phase 10 [Observability]:** Observability: OpenTelemetry deep dive, Prometheus metrics [histograms vs counters], Grafana, Jaeger, Log aggregation [Loki], Cost attribution logging. WHY: You cannot operate what you cannot see.

**Phase 11 [HARDENING]:** Networking: Rate limiting algorithms, K8s HPA concepts. Security: Threat modeling, SAST/DAST. Performance: k6 load testing, p95/p99 analysis, Postgres performance tuning, Redis tuning. WHY: Production readiness.

**Phase 12 [Deploy & OSS]:** Cloud: Kubernetes [Deployment, Service, Ingress, ConfigMap, Secret, HPA], Helm chart creation, Terraform IaC basics [VPC, RDS, ElastiCache]. Docker: Multi-stage builds, minimal images [distroless]. OSS: OSS licenses [Apache 2.0], community building, Release management. WHY: Shipping and scaling.

### PART 8: SPRINT SYSTEM

We run 1-week sprints. Not 2 weeks. Fast feedback is critical for small team.

**Definitions:**
*   Epic: Big deliverable [2-4 weeks] e.g., "Execution Engine"
*   Feature: Shippable subset of Epic [3-7 days] e.g., "Retry logic"
*   Story: User-centric [1-2 days] e.g., "As dev I can retry failed run"
*   Task: Engineering atomic work [<1 day] e.g., "Implement exponential backoff logic in worker"
*   Sprint: 1 week of Stories/Tasks
*   Milestone: Phase completion
*   Release: Tag that goes to staging/prod

**Templates:**

**Epic Template:** Title, Goal, Owner, RFC Link, Non-Goals, Deliverables [APIs, docs], Risks, Exit Criteria Checklist, Linked Stories.

**Story Template:** As a [role], I want [action] so that [value]. Acceptance Criteria [Gherkin]: Given/When/Then. Tech Notes, Dependencies, DoD reference.

**Task Template:** Title, Type [code/docs/test/infra], Estimate [hrs], Parent Story, Steps, Done when [checkbox].

**Sprint Template:** Sprint Goal [single sentence outcome], Planned Velocity, Stories In, Risks, Review Notes, Retro Learnings.

### PART 9: AI DEVELOPMENT WORKFLOW

We use a layered stack:

*   **Claude Code:** For large codebase refactors, planning, execution engine work. Strength: Long context reasoning.
*   **Cursor:** Primary IDE for 90% of implementation. Custom rules in `.cursor/rules/aether.md`.
*   **GitHub Copilot:** Autocomplete only. Never for architecture.
*   **ChatGPT:** For research, learning concepts, debugging rubber-duck.

**When AI MUST Be Used:**
*   Boilerplate generation after architecture is approved
*   Generating tests from spec [human reviews edge cases]
*   Generating SDK boilerplate from OpenAPI spec
*   Writing docs from code [but human must verify]
*   Explaining unknown codebase area

**When AI MUST NOT Be Used:**
*   Writing RFCs or ADRs from scratch [human must draft first, AI can polish]
*   Making build vs buy decisions
*   Deciding database schema or module boundaries
*   Final security reviews
*   Committing without human running and understanding code

**How Prompts Should Be Written [Context Engineering]:**

BAD: "Add retry logic"

GOOD:
Context: We are in execution-engine Phase 4. See RFC-0002 for queue choice and ADR-0004 for state machine. File: services/execution-engine/worker.go
Goal: Implement exponential backoff with jitter for failed job retries. Max 5 retries. Must be idempotent.
Constraints: Must use libs/common/retry package. Must update Prometheus metric aether_job_retry_total. Must not break existing tests in worker_test.go
Acceptance: Test scenario: Fail job 2 times then succeed - asserts retry count and delay. Failure injection test must pass.
Non-Goal: Do not implement dead-letter yet.

**Code Review with AI:**
Human asks Claude: "Review this PR for violation of provider-agnostic principle, missing traces, and security issues. Focus on modular boundary violation." AI is a linter, not approver. Human is approver.

**Debugging with AI:**
Share trace ID, logs, not just "it doesn't work". Prompt: "Worker is stuck in Running state for runId xxx. Here is trace from Jaeger, here is state machine diagram from docs. Hypothesis why?"

**Testing with AI:**
"Generate table-driven tests for function X covering: happy path, timeout, nil input, duplicate idempotency key. Use existing test helpers in libs/common/testutils." Then HUMAN adds missing edge: concurrent retries.

**Definition of Ready [To move from Backlog -> Ready]:**

*   RFC linked if required label
*   Acceptance criteria defined in Gherkin
*   No open questions tagged
*   Estimated <= 1 day if Task

**Definition of Done [To move to Done]:**
*   Code merged to main with PR approved
*   Unit + Integration tests passing with >80% coverage on new code
*   OpenAPI spec updated if API changed
*   Architecture doc updated if behavior changed
*   Metrics/logs/traces added for new flow
*   Runbook updated if operational
*   Manual smoke test in staging [if applicable]
*   No P0/P1 security issues

[ ] Integration test with real Postgres/Redis via testcontainers

### PART 11: ENGINEERING DECISIONS

**When to write RFCs:**
*   Any new Epic
*   Choosing technology [queue, DB, library with long life]
*   Changing public API contract
*   Any decision with 2+ viable alternatives that impacts >1 module

**When to write ADRs:**
*   Immediately after RFC approved
*   When you made an on-the-fly architectural call in PR that future you will question
*   When you reject an alternative after research

**When to refactor:**
*   Rule of Three: Third time you duplicate code / workaround -> refactor
*   When module boundary violated (e.g., registry imports execution table)
*   When adding feature becomes disproportionately hard
*   As separate PR, never mixed with feature PR

**When to redesign:**
*   When failure modes not covered [e.g., retry logic leaking memory]
*   When RFC assumptions invalidated by load test or security scan
*   Trigger: Write new RFC marked "Supersedes RFC-xxx"

**When to postpone work:**
*   If it doesn't serve current Phase goal [e.g., building UI dashboard in Phase 4]
*   If NFRs for future scale [e.g., sharding in V1]
*   Add to backlog with `postponed` label and add reasoning in issue

**How to avoid overengineering:**
*   Ask: "What is the simplest thing that could fail in production and still be fixed tomorrow?" Ship that.
*   No abstractions for 1 implementation. Wait for 2nd use case.
*   Prefer config over code for extension initially

**How to avoid technical debt:**
*   All `TODO:` must have linked GitHub issue number `// TODO(AET-123): ...`
*   Tech Debt bucket 20% every sprint
*   Lint rule: no `any`/`interface{}` without comment
*   Quarterly: Debt review from issues with `tech-debt` label, promote to Epic if needed
